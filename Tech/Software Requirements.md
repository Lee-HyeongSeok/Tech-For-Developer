## Software Requirements

***

1. 요구사항은 무엇인가
2. 요구사항은 어떤 행위들로 구성되고 정의할 수 있는가
3. 몇 가지 단순한 정의, 타당성으로 시작하여, 요구사항이 실제로 시스템을 구축하는 프로세스
4. 따를 가치가 있는 몇 가지 법칙



### 요구사항 접근 방법 3가지

1. 개발단계로 진행하기 전에 요구사항들을 자세하게 명세화하는 방법 - 전통적인 접근법
2. 가능한 빠르게 개발하기 위해 형식성과 문서화를 포기하는 방법 - 익스트림 접근법
3. 위 두가지를 절충한, 요구사항들을 일부 처음에 명세화하고 일부는 나중에 명세화하는 방법 - 증분 접근법



### 요구사항이란?

> 무엇이 필요한지, 어떻게 할지에 관한 것이 아니다.

- 풀어야 할 문제, 시스템의 목적, 이를 성취하기 위해 필요한 모든 것을 정의하는 것
- 해결책을 정의하는 것이 아님
- 어떤 시스템이 만족시켜야 할 하나의 측정 가능한 목표
- 기능적 요구사항
  - 시스템이 무엇을 할지, 어떤 행동들을 할 수 있을지를 가장 중요하게 정의함
- 비기능적 요구사항
  - 시스템이 가져야 할 성능, 보안, 표준 같은 특성
- 시스템을 만드는 순서를 결정하는데 있어서 가장 먼저 할 일은 각 요구사항에 대한 우선순위 부여



### 요구사항 명세

- 요구사항과 이를 이해시키기 위한 배경 자료들을 모은 문서
- 시스템이 가져야 하는 모든 **기능**과 **능력**에 관해 정의하고 있어야 함
- 명세의 목적은 생각을 소통하는 것



### 반복적인 작업

- 최종 목표가 합리적이고 명확한 전체 방향을 제공할 때 가장 효과적



### 폭포식 접근법

- 빠르게 진행되고 관여하는 사람이 적은 요구사항 단계에서는 강세
- 프로젝트의 남은 단계들이 더 명확하고 훌륭한 최종목표가 있을 때도 강세



### 개발 생명주기 순환

> 해당 모델은 어떤 방법론을 적용하던지 상관없이 유효하다.

1. Scope(범위 탐색)
   - 고객들의 의견을 반영한 시스템의 전체 동기와 목적에 대한 개략적인 설명
   - 즉 시스템의 목적
2. Requirements(요구사항)
   - 풀어야 할 문제의 상세에 대해 충분한 수준으로 정의하기.
   - 범위 탐색은 고객이 필요한 것을 말한 것이고, 요구사항은 실제로 필요한 것이다.
   - 불완전하고 비실용적인 면들을 인자하여 구체화 시킨다.
   - use-case 또는 프로토타입 같은 것들을 만드는 행위도, 해당 단계에서 이루어질 수 있음
3. Design(설계)
   - 요구사항 명세에 기반해서, 해결책을 공식화 하기
4. Development(구축)
   - 개발자가 설계의 모호한 점을 이해할 수 있게 해주고, 설계가 요구사항을 정확히 만족하는지 확인 가능한 단계
5. Testing
   - 시스템이 예상한대로 동작하는지, 요구사항을 만족하는지 확인하는 단계
6. Installation
   - 시스템 설치



### 요구사항 명세를 작성할 때마다 적용하게 될 몇 가지 원칙

1. **반복을 피하라**
   - 특정 정보를 담은 각 항목들은 한 번만 적는 것이 실용적
   - 반복은 추가적인 작업을 만들게 되고, 비 일관적인 결과물을 만들어 냄
2. **해결책이 아닌 문제를 기술하라**
   - 어떻게가 아닌 무엇을 정의해라
   - 문제를 해결할 자유가 필요
3. **문제와 해결책, 문제와 프로젝트를 별개로 다루어라**
   - 해결책을 강제함으로써 유연한 사고를 막지 않아야 한다.
